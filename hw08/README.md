Требования к реализации:

0. Подключить spring-boot-starter-data-mongodb +
1. Использовать Spring Data MongoDB репозитории, а если не хватает функциональности, то и *Operations +
2. Можно реализовать Flapdoodle Embedded MongoDB +
3. Как хранить книги, авторов, жанры и комментарии решать Вам. Но перенесённая с реляционной базы структура не всегда будет подходить
   для MongoDB. +
4. Покрыть интеграционными тестами (со встроенной БД) все сервисы, остальные тесты можно убрать +
5. В решении не должно остаться никаких следов других технологий доступа к данным (Jdbc/Jpa) +
6. Работа приложения не должна приводить к наличию данных, находящихся в неконсистентном виде
7. Учесть отсутствие каскадных операций (в т.ч. при использовании @DBRef) и то, 
   что MongoEventListener-ы по разному работают для разных методов, а в некоторых случаях и вовсе не сработают 
8. Без крайней необходимости из БД не должны тянуться лишние данные (пример - загрузка всех книг автора при его удалении или изменении).
   При необходимости, можно применить подход с расширением Spring Data репозиториев кастомным функционалом использующим MongoOperations
9. Организация данных в MongoDB и решение типовых проблем; интеграционное тестирование репозиториев с помощью @DataMongoTest. +

Рекомендации для 1:N - связей:
• Старайтесь внедрять, когда это возможно. Данные,
  к которым осуществляется совместный доступ как
  к единому целому, лучше и хранить вместе.
• Иногда имеет смысл комбинировать хранение:
  внедрить 10 последних отзывов в продукт, тогда как
  все отзывы хранятся в отдельной коллекции.


Рекомендации для M:N - связей:
• Внедряйте, если:
  доминирует чтение, а не запись
  повторяемость данных не проблема
  изменения на одной из сторон происходят чаще
• Ссылайтесь, если:
  много связанных сущностей
  изменения часто случаются в обеих сущностях
• Используйте смешанный подход для лучшей
  производительности
